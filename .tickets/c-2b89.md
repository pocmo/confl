## Research Findings

### How Confluence Cloud OAuth 2.0 Works

Confluence Cloud uses OAuth 2.0 (3LO - Three-Legged OAuth), which is the standard authorization code flow:
1. App redirects user to Atlassian auth page
2. User logs in and grants permission
3. Atlassian redirects back to callback URL with authorization code
4. App exchanges code for access token
5. Access token used to make API calls via api.atlassian.com

### Required App Registration

YES - Must register OAuth app in Atlassian Developer Console:
- Create app at developer.atlassian.com/console
- Configure callback URL (must match redirect_uri in OAuth flow)
- Get client_id and client_secret
- Add API permissions (Confluence API)
- Set required scopes

### Required Scopes

For read/write page access:
- **write:confluence-content** - Create, update, delete pages/blogs/comments
- **read:confluence-content.all** - Read all Confluence content
- **offline_access** (optional) - For token refresh/background access

Note: App permissions are still limited by user's actual permissions in Confluence.

### CLI OAuth Callback Approaches

Two main approaches for CLI tools:

**1. Localhost Callback (Browser Flow)**
- Most user-friendly for desktop environments
- Start local HTTP server on localhost (e.g., http://localhost:8080)
- Open browser to auth URL
- Server catches callback with auth code
- Exchange code for token
- Pros: Simple user experience, instant
- Cons: Requires browser, open port, not suitable for headless

**2. Device Flow**
- Better for headless/remote environments
- Display code + URL to user
- User visits URL on any device and enters code
- CLI polls for authorization
- Pros: Works in SSH, containers, no callback needed
- Cons: Extra steps for user, polling overhead

**GitHub CLI uses both:**
- Default: Device flow (reliable, works everywhere)
- Optional: Browser flow with --web flag

### Atlassian Device Flow Support

**NO** - Atlassian does NOT support OAuth device flow. Only Authorization Code flow is available.
This means localhost callback with browser is the ONLY option for OAuth.

### Python Libraries for Atlassian OAuth

**atlassian-python-api**
- Most popular: ~3M downloads/month
- Supports multiple auth methods including OAuth 2.0
- Has OAuth support but documentation is sparse on implementation details
- Would need to verify if it handles full OAuth flow or just token usage

**Manual Implementation**
- Use requests + webbrowser standard lib
- Start local HTTP server for callback
- Open browser to auth URL
- Exchange code for token
- Store token in credentials file

### Implementation Complexity

OAuth is significantly more complex than current API token approach:

**Current (API Token)**
- User creates token in Atlassian UI
- Runs: confl configure --site X --email Y --token Z
- Simple, works everywhere

**OAuth (Browser Flow)**
- Must register OAuth app (one-time, per developer/org)
- User runs: confl auth login
- CLI starts local server on random port
- Opens browser to auth URL with client_id, redirect_uri, scopes
- User logs in and grants permission
- Callback to localhost with code
- Exchange code for access token + refresh token
- Store tokens securely
- Handle token refresh when expired
- More moving parts, more failure modes

### Key Challenges

1. **App Distribution**: Each user would need the same client_id/secret OR each org creates their own OAuth app
2. **Secret Storage**: Client secret needs to be embedded in CLI (public client) - security concern
3. **No Headless Support**: No device flow means SSH/container users can't use OAuth
4. **Token Refresh**: Need to implement refresh token logic
5. **Complexity vs Benefit**: API tokens work fine for CLI use case

### Recommendation

**Do NOT implement OAuth for confl CLI at this time.**

Reasons:
1. API tokens are simpler and sufficient for CLI use case
2. No device flow means OAuth doesn't work in headless environments anyway
3. OAuth adds significant complexity with minimal benefit for end users
4. Most CLI tools (terraform, aws-cli, etc.) use API tokens/keys, not OAuth
5. GitHub CLI is special case - GitHub hosts the OAuth app, we'd need users to register their own

**Keep current API token approach:**
- Simple, secure, works everywhere
- User controls token in Atlassian UI
- No server/callback/browser dependencies
- Better for automation and scripting

### Alternative: Consider in Future

If we DO want better auth experience in future:
1. Host an official OAuth app (requires infrastructure)
2. Implement both browser flow AND a web portal for headless users
3. Add token refresh logic
4. Keep API token method as fallback
