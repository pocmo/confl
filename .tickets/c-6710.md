# DISCOVERY: Research rendering Confluence storage format as readable terminal output

Research approaches for converting Confluence storage format (XHTML) to nicely formatted terminal output.

## Problem
When fetching pages, Confluence returns content in storage format like:
```xml
<ul><li><p><ac:link ac:card-appearance="inline"><ri:page ri:space-key="PM" 
ri:content-title="Building, testing and distributing Android SDKs" ri:version-at-save="2" />
<ac:link-body>Building, testing and distributing Android SDKs</ac:link-body></ac:link></p></li></ul>
<ac:structured-macro ac:name="children" ac:schema-version="2" data-layout="default" 
ac:local-id="58a4a9e5-5d18-4f81-80bb-f912dcd0ac45" 
ac:macro-id="3b5a0d1f-6a62-44ac-8e40-5338b393a599" />
```

This is not human-readable. We need to render it nicely with Rich in the terminal.

## Questions to Answer
1. **What format should we request from the API?**
   - Storage format (XHTML with Confluence-specific tags)?
   - atlas_doc_format (ADF - JSON-based)?
   - view format (rendered HTML)?
   - Which format is best for terminal rendering?

2. **How do we convert to terminal output?**
   - Convert storage format → Markdown → Rich rendering?
   - Convert ADF → Markdown → Rich rendering?
   - Parse HTML/XML directly and render with Rich?
   - Use existing libraries or build custom parser?

3. **What Python libraries exist?**
   - HTML/XML to Markdown converters (html2text, markdownify, etc.)?
   - Confluence storage format parsers?
   - ADF (Atlassian Document Format) parsers/converters?
   - Rich has Markdown rendering - can we leverage that?

4. **How do we handle Confluence-specific elements?**
   - Macros (children, info, code, etc.)?
   - Internal links (<ac:link>, <ri:page>)?
   - Attachments and images?
   - Tables, mentions, emojis?
   - What should we display vs skip?

5. **Testing approach?**
   - Should we fetch real page samples for test fixtures?
   - What variety of content do we need (lists, macros, links, tables, code)?

**2026-01-14T20:45:25Z**

Discovery complete. Research documented in docs/architecture/content-rendering.md.

Key findings:
1. Recommend using STORAGE format from API (not ADF or view)
2. Rendering pipeline: Storage → Markdown → Rich
3. Leverage existing storage_to_markdown() converter (77+ tests)
4. Rich has excellent built-in Markdown rendering
5. No new dependencies required
6. Existing converter handles all major Confluence macros

Filed 5 follow-up implementation tickets:
